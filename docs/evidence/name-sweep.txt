The two hits are the same single file:
  .next/cache/turbopack/v16.3.5-ca2c75eb/00000003.sst

Cause, read directly out of that file: Turbopack's persistent filesystem cache
snapshots the environment variables of the shell that ran the build. The shell
used here exports a base URL and an agent name belonging to the operator's own
tooling, so those strings land in the cache file. Nothing in the source tree
contains them.

Containment, each proven rather than assumed:
1. The file is gitignored. `git check-ignore -v` on it returns
   ".gitignore:7:/.next/", so it cannot enter a commit.
2. The deployable artefact is clean. Scanning every file under .next except
   .next/cache for all of the terms above returns 0 files.
3. scripts/guard.sh now scans the build output as check 6, excluding
   .next/cache for the reason above, so this is enforced on every commit
   rather than checked once.

Update, 22 Sep 2026, after the first `next dev` run.

`next dev` wrote two agent instruction files into the repository root, one of
them named after an AI tool, and they were not caught by review: the guard
caught them. Fixed at the source with `agentRules: false` in the Next config,
the files deleted, and the names added to .gitignore.

Two scope corrections came out of the same run, both recorded in RESEARCH.md:

1. Check 6 excludes `.next/dev` as well as `.next/cache`. Next.js 16 gives dev
   and build separate output directories and only the build output ships.

2. Check 6 scans the deployable output for the client, sister company, person
   and platform names only, not for AI tool names. A vendored dependency
   carries such a string in a docstring inside its own source map, which is
   not ours to remove and is not evidence of anything. Everything this
   repository authors is still checked for both sets.

The guard also now checks file and directory names (check 7), because a file
named after a banned term was invisible to a content scan. The self test
covers it.
